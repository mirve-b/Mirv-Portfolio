ABSTRACT
 
iii
KAEL is an innovative online library and portfoliocreator that strives to improve student
productivity and career readiness. At present, university students create a diverse range of
academic and creative work using specialized resources. It is a waste of time to gather and
organize everything when applying for jobs or studying abroad, which can take weeks. KAEL
is composed of Flutter, Darts, and Firebase. Every day, individuals utilize a central
workspace to record information, upload their projects and organize it automatically. The
primary objective is to convert the daily tasks of students into aesthetically pleasing
professional portfolios or CV links that can be shared immediately. Additionally, this
website promotes student work through online platforms like Glassdoor for academic
purposes. By focusing on their work, students can quickly see the benefits of doing so in
their careers. The platform was created by two Computer Science students and has an
elaborate future plan.

CHAPTER 1: INTRODUCTION
The domain is an intelligent, high availability web and mobile web system that processes,
analyzes and handles academic file hosting, deep knowledge parsing and dynamically
renders the layout of career assets.
The end-users may be engineering students, researchers or academic professionals of national
and international origin but the main target area will be across Pakistan. The user operates the
software to safely keep academic project documentation, research notes, source code
repositories and media assets. The user can choose to upload information to the advanced
language model pipelines in the cloud, or can carefully 
The field of software engineering has seen rapid developments, and other areas like cloud
computing have revolutionized the way technical accomplishments, universal discoveries and
research findings are shared and sold to the global industry. The current learning and working
environment is saturated with a tremendous amount of unstructured, technical information—
whether it's complex source code repositories or local project files. However, achieving these
unprocessed assets into professional and persuasive stories is a big challenge. Most technical
personnel can perform analytical work well, but are challenged with designing their portfolio
in a visual format, establishing their strategy, branding it and copy editing. So critical
engineering proofs are frequently hidden in local directories, not to be available in the
clamorous recruitment channels.
KAEL, with its new features of Natural Language Processing (NLP) and seamless 
cross-platform mobile web environments, is changing the way people create portfolios 
by combining traditional thinking. Users are not asked to make a long list of case studies 
for a project, build a layout matrix or create a hierarchy of index keywords from ground 
up, instead, the system sets up an automated pipeline to work. Here, the person who 
occupies the property gives just the basic analytical facts, and the system intelligence 
builds the organized professional story.

CHAPTER 2: EXISTING SYSTEM
2.1 Relative Work
On closer inspection, today's software solutions are seen as two separate, standalone
paradigms: digital storage libraries and automatic portfolio/web-building platforms. Cloud file
storage is a reality; services such as Google Drive, Dropbox, and even dedicated institutional E-
repositories are highly secure and reliable, but are passive file hosting servers with no
capability to read or understand files and gain contextual business value from them. By
comparison, simple resumes like text files can be built with modern resume and portfolio tools
such as Kickresume and Rezi, but the project file can't be a mixture of different files, which
these tools cannot handle to dynamically create an interactive project portfolio gallery.
Obviously, there are no intelligent cross- over systems that can automatically generate the web
presentation frameworks from raw files.

CHAPTER 3: SOFTWARE PROCESS MODEL
3.1 Software Process Model
A software process model is a structured framework that outlines the activities,
milestones, and deliverables in developing, designing, building, testing, and deploying 
a software system. It thus provides a development team with a disciplined approach to
managing scope, time, quality, and risks to ensure that the developed product will satisfy
its intended users. The process model is usually selected early because it lays down how
requirements will be gathered, how work will be done, how progress will be assessed,
and how feedback will be handled on the developed product.
In contrast, traditional process models like the Waterfall embody a linear, sequential approach:
each phase - requirements, design, implementation, testing, deployment, and maintenance -
wholly precedes the other. This approach best fits processes where requirements are clear
from the start and fixed, technology is well-understood and known, and immediate response to
iterative feedback from one developer is very fast. Since the KAEL project applies AI pipeline
development iteratively, in which features are added continuously and, at times, may even
need to be removed, coupled with the fact that this is a single-developer team, an iterative and
incremental process model fits better than the pure sequential model.

3.2.1 Why Agile Scrum was chosen
Agile Scrum is chosen because of the following reasons:
Uncertain and changing requirements: KAEL relies on behaviour that evolves and changes - such as
extracting skills, generating case studies, formatting CVs - and only the actual confidence in the output
quality can be judged by building, testing and refining prototypes, not by designing it upfront. Doing so by
delivering value incrementally in sprints enabled a snapshot of a working system (e.g., upload data,
process data using AI, generate case studies, export the CV), to be created at the end of each sprint,
before the complete system would be developed.
Flexibility for one developer: Scrum's light ceremonies — sprint planning, daily self review, sprint review,
retrospective — can be reduced to one person and still maintain the discipline of prioritised backlog and
time-boxed delivery.
Risk reduction: AI components (data extraction, summarisation, ATS compliant formatting) had the
highest technical uncertainty; this meant that tackling these in early sprints meant that integration
risks were raised but there was still time left in the project lifecycle to adapt the design.

CHAPTER 5: SYSTEM DESIGN
5.2 UI/UX Design
KAEL's interface adopts a dark theme and a minimalist style that uses a semi-permanent
navigation sidebar located on the left-hand side of the screen, providing users with consistent
access to its core modules while they are using it. Onboarding is designed to be guided and
progressive with a step-by-step approach while a flexible canvas-based environment will be
provided for project and portfolio management going forward. The interface has the following
main sections:
Landing & Authentication: This is the first place a user will interact with the application,
such as the landing page and sign-up/login screens.
5.1 Brief Description
KAEL (Smart Portfolio Builder and Academic eLibrary) is a desktop application built with Flutter
that takes a student's raw academic data and creates structured and professional assets that are
ready for use in the world of careers. It is a realization of the scope of the KAEL roadmap, which
was developed using an Agile Scrum process over four sprints. Onboarding gathers personal,
educational and professional information and saves it in Firebase Firestore, which is then used by
the Gemini API to create a professional biography. Users then upload all the raw academic
content (notes, assignments, certificates, PDFs, images, screenshots etc) to Firebase Storage
and add metadata to Firestore. This information is used, along with the user's information, to
create a structured case study and to update the user skills and role, which is passed on to the
Gemini API. The approved case studies are grouped in publishable portfolios that have a
shareable URL and QR code. A Job Match module also parses the job descriptions and creates a
personalized and ATS-friendly CV. The system is designed in the client-server model as the
desktop side of the system is implemented using Flutter, and the server side is implemented
using authentication, Gemini API calls, Firestore for data, and Firebase Storage for files. The
interface, ER diagram, DFDs, activity diagram, class diagram, sequence diagram and architecture
are described in detail in sections 5.2- 5.8.

CHAPTER 6: DEVELOPMENT
6.1 Selection of Tools & Technology
Dedicated client-side workstation environments were synced to cloud-based hardware layers
for the compilation, engineering and localized rendering of the KAEL ecosystem. The following
is a minimum local system configuration to support the execution of concurrent threads in the
environment and compilation workloads on multiple platforms:
6.1.1 Hardware
Central Processing Unit (CPU): At least 4 physical cores — Intel Core i5 / AMD Ryzen 5
processor with clock speed optimizations to support heavy development tools and
active mobile device emulators.
Random Access Memory (RAM): 8G to 16G DDR4 RAM – provides high speed and
structural stability as the application framework is being compiled during the hot-
reload process.
Solid-State Storage (SSD): At least 256 GB NVMe SSD storage for faster read/write
cycle processing speeds for asset caching, dependency fetching and index
compilation.
Testing Hardware: Verification on multi-architecture was done by running different
screen-aspect configurations on the various physical Android devices and using a
combination of standard x86 and ARM-based browsers to ensure uniformity.
The cloud infrastructure tier is fully managed and distributed hardware infrastructure servers
managed by Google. A cluster of these servers also hosts dedicated tensor processing units
(TPUs) to enable the low latency calls to the application's cognitive inference modules.

broad platform cross-compatibility. The software stack integrated is defined by the following

CHAPTER 7: SOFTWARE TESTING
7.2 Testing Process
The overall testing process:
7.1 Software Testing
Software testing is the process of examining a system in a methodical way to ensure that it
performs as expected, satisfies its requirements, and is reliable under realistic circumstances.
Testing is especially significant for KAEL for a number of reasons related to the characteristics of
the system.
Firstly, KAEL's value proposition relies on the accuracy and trustworthiness of AI-generated
content — the case study, biography, or CV that misrepresents a user's abilities or fabricates
information would be a serious problem for the platform, and it's not just a matter of
aesthetics, as it would serve no useful purpose. Second, the system is comprised of several
independent services (Firebase Authentication, Cloud Firestore, Firebase Storage, and the
Gemini API) that are communicating via HTTPS; if any one of these service integration points
fails or is inconsistent, then user data may be corrupted, or the entire end-to-end system may
end up broken, with the user never realizing what happened. Third, since KAEL is the product
of a team of only one developer and a set academic timeframe (Table 4.2), there was no
dedicated QA team to identify regressions — meaning that structured and repeatable testing
throughout each sprint (not just at the end of the development period) was crucial for finding
defects early, when they are cheapest to fix. Lastly, the final CV output is to be ATS compliant 
and to the recruiter, formatting and data-integrity issues that might be suitable for an internal
tool were treated as high priority defects, due to the direct impact on a user's job 
or internship opportunity.
Testing was embedded into the Agile Scrum flow described in Chapter 3, rather than treated as
a final stage after development. Each of the four sprints ended with a Sprint Review where the
new increment was manually exercised, with defects recorded and prioritized at the Sprint
Retrospective for resolution in the next sprint.
51
Unit testing: Individual functions and UI elements (e.g., form validation, upload type checks)
tested as they were built, to catch simple logic errors early.


=====PAGE 62=====
Black box testing has been used as the main testing technique for KAEL — the system was tested
with respect to its inputs and outputs only and its code structure was not taken into
consideration. The application of this method was especially suitable for KAEL in two ways. First,
several of the most important behaviours of the system itself (case study generation, bio
generation, job match scoring) are also generated by the Gemini API itself, which, from the point
of view of the application, is a black box because the correctness of the behaviours can only be
judged by the quality of what it spits out on a given input, not by looking at the internal logic which
the application is not responsible for controlling. Second, black box testing directly validates the
system against user facing requirements (e.g. uploading a PDF and profile data should create a
structured case study with all of the required sections), making it an obvious fit for verifying user
acceptance criteria set in Sprint Planning.
These are the black box techniques that were used:
Equivalence partitioning: Break down the domain of the input into valid and invalid subsets
of input (e.g. supported file types: PDF/PNG/JPG and unsupported file types: other) and test
one sample input from each subset instead of testing all possible inputs.
52
Integration testing: Conducted mostly in Sprint 4, verifying data passed correctly
between modules (e.g., a file in Firebase Storage correctly referenced in its Firestore
project record, and data sent to the Gemini API received and persisted correctly).
Functional (black box) testing: The primary technique used throughout the project,
ensuring each feature produced the expected output for a given input, without reference
to internal implementation.
Usability testing: Informal testing with sample users performing realistic tasks (registering,
uploading a project, generating a CV), per the project priority in Table 4.2 requiring 90–95%
of user-acceptance tests to pass for Release 1.0.
Regression checks: After each bug fix or sprint's changes, previously verified features were
manually re-checked to ensure new functionality didn't break existing behavior.

CHAPTER 8: IMPLEMENTATION AND TRAINING
8.1 Implementation
The implementation phase of the KAEL ecosystem is the transition stage from
conceptual modules to an active state of production of the KAEL project. This was done
in a modular way, layer after layer of the systems were implemented in order to
maintain the integrity of data tracking:
56
Backend Environment Setup: This was to prepare the workspace for the Google
Firebase project. In this workspace, Firebase Authentication was setup to handle user
sessions safely, Cloud Firestore collection schemas were created to store relational
JSON metadata and the Firebase Storage bucket directories were instantiated to
contain raw user media payloads.
API Integration Layer Execution: Node.js serverless scripts were written and deployed as
the Firebase Cloud Functions. These routines serve as the safe and secure access points for
the Google Cloud AI services. They consume raw document streams from storage, compile
payloads with optimized behavioral system prompts and call the appropriate secure
asynchronous REST APIs to the Google Gemini / Imagen API endpoints.
Frontend Interface Construction: Flutter SDK's were used to build the user interface layer.
To create state orchestration workflows, clean architecture patterns (e.g., Provider or BLoC)
were adopted and the asynchronous state changes were mapped directly to the UI layer.
This configuration makes it possible to have file upload progress bars, live markdown
previews, and dynamic theme changes to work smoothly in mobile and web clients.
Operational End-to-End Pipeline Binding: The last step was to connect the client
application with the cloud functions directly. This full binding can be used by a user to
drop an unstructured document, activate an automated semantic extraction pipeline,
and immediately receive updates to that document's Firestore metadata in JSON
format, and render a web portfolio page with interactive features that can be hosted,
and have it generate an ATS-friendly CV.

8.2 Project Overview (Key Features only)
The selective capabilities delivered in the deployed KAEL ecosystem are limited to the
maximization of automation, data fidelity and creative control for the academic user:
57
Multimodal 'Cell' Ingestion: A modular drop-terminal that can be used to ingest
unstructured academic inputs from a number of media extensions (PDFs, DOCX files, raw
project screenshots, audio elements and video clips) to form a permanent, secure cloud
archive.
Automated Semantic Extraction: Direct real-time deep analysis of Google Gemini API to
clean and process messy project information and instantly produce detailed text summaries,
case studies, technical or soft skill mapping and dynamic filter tags.
One-Click Intelligent Portfolio Building: Automated web template engine that
instantly combines onboarding profile states with extracted project data and renders a
clean and customizable page for the portfolio with no copywriting needed.
Generative Asset Synthesis: Direct integration with the Imagen API, users can generate high-
quality and thematic project background banners and shape their digital identity with professional
AI-generated headshots or custom character models.
Recruiter-Ready ATS CV Engine: The document compiler designed specifically for ATS that can
convert form data and AI-mapped skill sets into a monochrome CV format that passes through the
automated applicants.
Expected Outcome
Successfully implemented KAEL is a high performing, responsive across-platform environment
that spans between the messy hard drive and professional network. The anticipated structural
outcome is that students will no longer have to do manual engineering of web structure and
resuming copy. Users get a universal link to their portfolio canvas on the web, which is live and
easily accessible, with an ATS-friendly, perfectly formatted CV document preformatted for
competitive corporate evaluations.

8.3 Training
With an AI-powered, highly automated platform like KAEL, it is essential to have a well-defined
and structured onboarding process to ensure that users can navigate the system smoothly and
maximize documentation benefits. The onboarding process for highly automated, AI-powered
platforms such as KAEL must be clear and structured to ensure users can interact with the
system efficiently and maximize the benefits of documentation.
Required Skillset
Basic Digital Literacy: Familiarity with standard operating systems, directory navigation,
and file system execution (such as dragging, dropping, or selecting items within local hard
drives).
Core Professional Self-Awareness: A knowledge and understanding of one's educational
journey, basic contact details and high-level career goals for the onboarding introduction
fields.
Artifact Assessment: The ability to critique AI case studies or skill maps when they are
localized or specific to certain contexts or industries, ensuring that the localized detail is
within the project's scope.
User Training Protocol
A structured three-layer approach to training and navigation is embedded within the application
ecosystem for a faster uptake of users and for ensuring high fidelity output:
Context-Aware Interactive Walkthroughs:
 The Flutter frontend automatically steps through a tutorial that guides the user through the visual
elements when the user logs in for the first time. This interactive guide is designed to show users
the navigation panel and how to upload a file to "The Cells," while also not overwhelming them
with the customizer.
Inline Reference Documentation and Tooltips: Specialized info markers and baseline
definition sections are inserted throughout the workspace interface, but without
interrupting the user's work. Clear descriptions of system terms, like what a "Cell"
represents or how the ATS CV engine handles text markers in the workflow, do not confuse
users when they use the system in a real workflow.
